# Kodolog

**Kodolog** — ассистент для проверки учебного Python-кода: статический анализ (AST), изолированный прогон тестов, LLM-ревью с валидацией ответа через Pydantic и генерация синтетических тестов. Один пайплайн, четыре инструмента, ноль боли.

Написан студентом 1 курса направления «Инженерия искусственного интеллекта» Университета ИТМО как пет-проект к заявке в учебно-научную лабораторию AIST (сезон 2026/2027).

## Зачем это нужно

Проверять студенческие работы вручную медленно, а доверять эту работу только LLM — ненадёжно: модель может пропустить падающий тест или «простить» голый `except`. Kodolog решает эту задачу гибридно: всё, что можно проверить детерминированно, проверяет код; LLM получает уже размеченный контекст и пишет человеческое резюме, которое строго валидируется схемой.

Проект сознательно перекрывает сразу несколько направлений лаборатории:

| Возможность Kodolog | Куда ложится |
|---|---|
| LLM-ревью с подсказками вместо готового решения | ИИ-ассистенты для обучения программированию |
| Pydantic-схемы ответов LLM, синтетические смок-тесты | Генерация синтетических данных для валидации агентов |
| Автозапуск тестов + статический анализ работ | ИИ-проверка студенческих работ |
| Метрики по набору работ: score, pass rate, топ правил | Анализ и адаптация бенчмарков |
| Каталог работ → JSONL-датасет + совместная встречаемость ошибок | Сбор и анализ открытых данных |

## Быстрый старт

```bash
git clone https://github.com/<ваш-логин>/kodolog.git
cd kodolog
pip install -r requirements.txt   # pydantic + requests, больше ничего
python -m kodolog --help
```

Из коробки работает **офлайн**: без ключа API ревью делает детерминированная заглушка `MockLLMClient`, так что демо запускается за минуту на любой машине.

### 1. Статический анализ

```bash
python -m kodolog analyze examples/submissions/bad_solve.py
```

```json
{
  "path": "examples/submissions/bad_solve.py",
  "lines": 47,
  "functions": 3,
  "issues": [
    {
      "code": "W003",
      "title": "изменяемый аргумент по умолчанию",
      "severity": "error",
      "line": 11,
      "hint": "значение по умолчанию создаётся один раз при импорте; используйте None"
    },
    {
      "code": "W002",
      "title": "голый except",
      "severity": "error",
      "line": 17,
      "hint": "ловите конкретное исключение, например ValueError"
    }
  ],
  "score": 52.0
}
```

*(Полный вывод содержит 10 замечаний — здесь сокращено.)* Правила: `W001` функции без докстринга, `W002` голый `except`, `W003` изменяемый аргумент по умолчанию, `W004` функция длиннее 40 строк, `W005` затенение builtins, `W006` `== None`, `W007` TODO/FIXME, `E001` `global`.

### 2. Прогон тестов в изоляции

Чужой код запускается в **отдельном процессе с таймаутом**: зависшее решение не подвесит проверяющего.

```bash
python -m kodolog test examples/test_submissions.py
```

```json
{
  "path": "examples/test_submissions.py",
  "total": 5,
  "passed": 4,
  "failed": 1,
  "results": [
    {
      "name": "test_submissions.TestBuggySolve.test_fizzbuzz_includes_n",
      "status": "fail",
      "detail": "14 != 15"
    }
  ]
}
```

### 3. LLM-ревью

```bash
python -m kodolog review examples/submissions/bad_solve.py --tests examples/test_submissions.py
```

```json
{
  "overall": "Работа выглядит как типичное решение первокурсника: статический анализ нашёл 10 замечаний (ошибок: 2). Тесты: 4/5 зелёные. Начните с ошибок уровня error — они ломают поведение, остальное косметика.",
  "hints": [
    {
      "area": "строка 11: изменяемый аргумент по умолчанию",
      "text": "значение по умолчанию создаётся один раз при импорте; используйте None",
      "severity": "error"
    }
  ],
  "grade": 1,
  "model": "mock (офлайн-режим)"
}
```

Ответ модели валидируется Pydantic-схемой `Review`: если LLM вернула мусор, `parse_review()` кинует `ReviewParseError` вместо того, чтобы показать пользователю сломанный JSON.

### 4. Синтетические тесты

```bash
python -m kodolog synth examples/submissions/good_solve.py --out generated_tests
```

```text
[template] generated_tests/synth_1_test_solve.py  —  смок-тест: good_solve.solve импортируется и вызываем; сигнатура: (numbers)
[template] generated_tests/synth_2_test_count_words.py  —  смок-тест: good_solve.count_words импортируется и вызываем; сигнатура: (text)
```

Офлайн — шаблонные смок-тесты (импорт + вызываемость), с включённым API — тесты, сгенерированные моделью по коду функций.

### 5. Датасет и метрики

```bash
python -m kodolog dataset examples/submissions --out data.jsonl
python -m kodolog metrics examples/submissions --tests examples/test_submissions.py
```

```text
записей: 3, суммарно замечаний: 10, средний score: 84.0/100
совместная встречаемость замечаний:
  W001 -> W002×1, W003×1, W005×1, W006×1, W007×1
  ...

Файлов: **3**, суммарно замечаний: **10**
Средний score: **84.0 / 100**, средний размер: **26.7 строк**
Доля зелёных тестов: **80%**
Топ правил: `W001` ×3, `W006` ×2, `W003` ×1
```

JSONL-формат — тот же, что используется в датасетах для LLM: каждая работа становится одной строкой с метриками, готовой к дальшейшему анализу.

## Архитектура

```text
                    ┌────────────────────────────────────────┐
                    │                cli.py                  │
                    │   analyze / test / review / synth /    │
                    │        dataset / metrics               │
                    └───────┬────────────────────┬───────────┘
                            │                    │
              ┌─────────────▼──────┐   ┌──────────▼──────────┐
              │    analyzer.py     │   │      runner.py      │
              │  AST-анализ кода   │   │ тесты в subprocess  │
              │  (без запуска)     │   │  + таймаут, JSON    │
              └─────────────┬──────┘   └──────────┬──────────┘
                            │                     │
                            └──────────┬──────────┘
                                       │
                            ┌──────────▼──────────┐        ┌─────────────┐
                            │     reviewer.py     │◄──────►│    llm.py   │
                            │ промпт + валидация  │        │ API / mock  │
                            │ ответа (Pydantic)   │        └─────────────┘
                            └─────────────────────┘
              ┌─────────────────────┐   ┌──────────────────────┐
              │      synth.py       │   │  dataset.py +        │
              │ синтетические тесты │   │  metrics.py          │
              └─────────────────────┘   │ данные и метрики     │
                                        └──────────────────────┘
```

Все модули обмениваются строго типизированными Pydantic-моделями из `models.py` (`Issue`, `StaticReport`, `TestReport`, `Review`, `GeneratedTest`, `DatasetRecord`, `MetricsSummary`) — ошибка в данных ловится на границе модуля, а не в глубине пайплайна.

### Ключевые инженерные решения

- **Тесты чужого кода — только в subprocess.** Решение студента может зависнуть или уронить интерпретатор, поэтому раннер запускает отдельный процесс с таймаутом и возвращает результаты одной JSON-строкой с маркером.
- **Гибрид вместо «всё на LLM».** Детерминированные проверки делает код; модель только пишет резюме — и не может «забыть» про падающий тест, потому что он уже в промпте.
- **Любой ответ LLM валидируется схемой.** `parse_review()` переживает markdown-заборы и лишний текст вокруг JSON, но невалидную структуру или `grade: 42` отклонит Pydantic.
- **Работа офлайн из коробки.** `MockLLMClient` читает машинночитаемый блок данных из промпта и собирает правдоподобный ответ — весь пайплайн демонстрируется без ключа и сети.
- **Деградация вместо падения.** Если LLM-режим генерации тестов вернул неожиданный формат, модуль откатывается к шаблонным смок-тестам.

## Включение настоящей LLM

Kodolog работает с любым OpenAI-совместимым API (OpenAI, OpenRouter, vLLM, локальные прокси):

```bash
export KOODOLOG_API_KEY="sk-..."          # или OPENAI_API_KEY
export KOODOLOG_BASE_URL="https://api.openai.com/v1"   # необязательно
export KODOLOG_MODEL="gpt-4o-mini"                     # необязательно
python -m kodolog review examples/submissions/bad_solve.py --tests examples/test_submissions.py
```

Клиент делает до 3 попыток с экспоненциальной паузой на 429/5xx.

## Структура проекта

```text
kodolog/
├── kodolog/
│   ├── models.py      # Pydantic-схемы всех данных
│   ├── analyzer.py    # статический анализ (AST)
│   ├── runner.py      # тесты в изолированном subprocess
│   ├── llm.py         # OpenAI-совместимый клиент + mock
│   ├── reviewer.py    # промпты, парсинг и валидация ревью
│   ├── synth.py       # синтетические тесты к функциям
│   ├── dataset.py     # каталог работ → JSONL + co-occurrence
│   ├── metrics.py     # сводные метрики и Markdown-отчёт
│   └── cli.py         # командный интерфейс
├── examples/
│   ├── submissions/   # три учебные работы: good / bad / buggy
│   └── test_submissions.py
└── tests/             # 31 юнит-тест самого Kodolog
```

## Тесты

```bash
python -m unittest discover -s tests   # или: python -m pytest tests/
```

31 тест покрывает анализатор (все правила и score), раннер (подсчёты, детали падений, таймаут зависания, битые файлы), LLM-слой (mock, парсинг мусорных ответов, полное офлайн-ревью), метрики, датасет и генератор.
